# TEMPORARY Render upload-boundary probe (test-only)

Disposable probe to measure, empirically, whether a Render **Free** web service
accepts request bodies up to ChopLab's original 1,024 MiB audio cap (plus
multipart overhead) and whether Render's edge streams or buffers them. It is
**not** part of ChopLab, touches no application code or audio processing, and
must be deleted after use.

## What it does

- `server.py` (stdlib only, Docker): binds `0.0.0.0:$PORT`.
  - `GET /healthz` – unauthenticated liveness; reports `max_bytes`.
  - `POST /probe` – bearer-authenticated (`PROBE_TOKEN`, constant-time
    compare, checked before any body byte is read). Reads the body in ≤1 MiB
    pieces through SHA-256 and discards it (never stored). Supports
    `Content-Length` and `Transfer-Encoding: chunked`; rejects missing length
    (411), declared length > max (413 before reading), and aborts chunked
    bodies at `max_bytes + 1` (413). One upload at a time (429 otherwise),
    120 s socket read timeout. Every app response carries `X-Upload-Probe: 1`.
  - `GET /progress?id=<upload-id>` – authenticated, out-of-band view of bytes
    received so far for the upload tagged with `X-Probe-Upload-Id`.
  - Logs only the request line and status (never headers, token or bytes).
- `client.py` (stdlib only): streams deterministic synthetic bytes (SHAKE-256
  1 MiB block, block index stamped in the first 8 bytes), optionally wrapped
  as `multipart/form-data` (`file` part, 178 bytes of overhead), using
  `Content-Length` or chunked framing; memory use is bounded at ~1 MiB.
  Requires `https://` unless `--allow-http`. Verifies the returned length and
  SHA-256 against what it actually sent.
- `run_suite.py`: runs the bounded matrix below and writes JSON lines.

Token sources (never argv, never printed): `PROBE_TOKEN` env var,
`--token-file <private file>`, or `--token-dpapi-file <file>` (Windows
CurrentUser DPAPI blob, raw or `ConvertFrom-SecureString` hex).

## Outcomes and what each proves

| outcome | meaning |
|---|---|
| `ok` | App received exactly `body_bytes` with matching SHA-256. Proves the edge delivered that body size intact with this framing. |
| `application_rejected` | Response has `X-Upload-Probe: 1` → the probe app itself answered (401/411/413/429…). |
| `platform_rejected` | HTTP response **without** `X-Upload-Probe` → generated by Render's edge (e.g. 413/502/503). Body excerpt and `rndr-id`/`server` headers are captured. |
| `integrity_mismatch` | App returned 200 but length/digest differ → body altered or truncated in transit. |
| `connection_aborted` | Connection dropped with no readable response; `server_progress_after` (authenticated, out-of-band) shows what the app actually saw, distinguishing an edge cut (app saw fewer bytes / `aborted`) from an app rejection. |
| `client_or_network_failure` / `client_failure` | DNS/TCP/TLS failure before any body byte, or local misconfiguration (no token, non-HTTPS URL). Says nothing about Render limits. |

- `framing_seen` vs. `framing_sent` (`edge_reframed`): whether the edge
  converted chunked↔Content-Length. `framing_seen=content-length` for a
  chunked upload implies the edge buffered the full body to compute a length.
- **Streaming** is claimed only by `--two-phase`: the client sends a first
  slice (default 8 MiB), then **withholds the rest** and polls `/progress` on a
  separate authenticated connection for `--pause-s` seconds. `streaming:
  "proven"` means the app reported received bytes > 0 while the client still
  held the remainder, i.e. the edge forwarded bytes before the request was
  complete. `"inconclusive"` means no such observation (the edge may buffer, or
  buffer at least the first slice); final byte counts and timings alone are
  **never** treated as streaming evidence.
- `server_max_rss_kib` (Linux) shows the probe's own memory stayed bounded.
- A pass proves the body size reached a *probe* container; it does not prove
  the real app handles it within 512 MiB (that is the app's concern).

## Matrix (`run_suite.py`)

1. missing token → expect app 401
2. declared Content-Length > probe max → expect app 413 before body
3. 100 MiB raw, Content-Length, two-phase
4. 100 MiB raw, chunked, two-phase
5. fixture 230,400,044 B raw, Content-Length
6. fixture multipart (230,400,222 B), Content-Length
7. 1,024 MiB multipart (1,073,742,002 B), Content-Length, two-phase
8. 1,024 MiB multipart, chunked
9. (`--include-stream-over-max`) chunked body > probe max → expect app 413 mid-stream

Default probe max is 1,200 MiB (`PROBE_MAX_BYTES`), above the 1,024 MiB +
multipart case and well below anything unbounded.

## Render deployment (Free, no other resources)

- New → Web Service → this repo, branch `michaelabatetsu-render-upload-boundary-probe`
- Runtime: **Docker**; Root Directory: `tools/render-upload-probe`;
  Dockerfile path: `./Dockerfile`; Instance type: **Free**
- Health check path: `/healthz`; Auto-deploy: off
- Environment: `PROBE_TOKEN` = the private synthetic token (≥32 chars; set in
  the dashboard only). Optional: `PROBE_MAX_BYTES` (default 1258291200).
- Do not add disks, databases or a payment method.

## Running against Render

```powershell
python client.py --url https://<svc>.onrender.com --health
python run_suite.py --url https://<svc>.onrender.com --token-dpapi-file <path\to\token.dpapi> --out render.jsonl
# single case, e.g. the cap boundary:
python client.py --url https://<svc>.onrender.com --size cap --multipart --two-phase --token-dpapi-file <...>
```

Free instances spin down when idle; call `--health` first and wait for 200.

## Local / CI validation

- Local: `PROBE_TOKEN=<synthetic> PORT=18080 python server.py`, then
  `python run_suite.py --url http://127.0.0.1:18080 --allow-http --include-stream-over-max`.
- CI (`.github/workflows/upload-probe-selftest.yml` → `ci_selftest.sh`): builds
  the image, runs it with `--memory 512m`, runs the full matrix, and validates
  the classifiers through nginx TLS controls: streaming proxy → `proven`,
  buffering proxy → `inconclusive` + reframed to Content-Length, 1 MiB-limited
  proxy → `platform_rejected`. Fails if the token appears in any log/result.
